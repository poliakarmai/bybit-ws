# REVIEW.md — правила ревью для bybit-ws

> Для AI-ревьюеров (Лена, Пётр, judge, сабагенты) и человека.
> Цель: ревью = поиск поломок, а не обсуждение вкуса. Каждое замечание = файл + строка.

## Что считается ПОЛОМКОЙ (критично)

1. **Документация врёт** — путь, цифра или поведение защиты не совпадает с кодом
   (прецедент: BlackSwan «закрывает 50%» — в коде только alert).
2. **Конфиг шлёт запросы не туда** — неверный base_url, неверный ключ/отрёзанный символ,
   RPC-эндпоинт не тот. Прокси/TLS не выключать.
3. **Кеш возвращает устаревшее** — снапшот выдан как live-данные (числа из AGENTS.md ≠ state.db).
4. **Числа из БД с неверным фильтром** — авто-сделки ОБЯЗАТЕЛЬНО `manual=0`; без фильтра
   завышение (332 vs 301).
5. **Мёртвое поле/функция, которое выглядит работающим** — объявлено, но никто не читает
   (`grep -rn` по нужности перед «баг высокой важности»).
6. **Severity выше косметики без трассировки вызывающих** — «неверная цена SL» ≠ баг,
   если `sl_price` нигде не потребляется.
7. **Остатки старого** — старые значения в файлах, которых не было в ТЗ
   (грепать ВСЁ, не только список из ТЗ; исключение: CHANGELOG/history легально содержат старое).

## Что НЕ считается поломкой (пропускать)

- Несущественные стилевые замечания: переименования, рефакторинг «на будущее», перенос строк.
- Снапшот в AGENTS.md устарел — это stale-safe by design, живые числа из RPC/state.db.
- Звучание комментария, если код верный.
- ≤ 3 мелких замечаний без влияния на деньги/корректность — не блокируют.

## Правила замечаний

- **Каждое замечание — файл:строка + цитата.** Без этого не принимать всерьёз.
- **Класс ошибки целиком** — «все места где используется X», не один инстанс.
- **«Исправлять нечего» — так и писать.** Не высасывать замечания ради количества.
- **Не повторять уже опубликованные замечания** — новый проход смотрит ТОЛЬКО новый diff.
- **3 раунда правок → стоп.** Не бесконечный цикл «нашёл старые проблемы порциями»:
  59% замечаний после 3-го раунда — про первое прохождение. Остановиться и пересмотреть подход.
- **После 1-го раунда — только новый diff.** Перечитывать полный файл заново запрещено:
  это и есть механизм «нахожу старые проблемы по одной за раунд».
- **Флаг класса, а не инстанса** — «grep -rn \"<параметр>\" по всему репо», «все места, где
  читается `cfg.strategy.*`». Автор закрывает все вхождения в том же коммите.
- **Каждый finding закрывается явно:** фикс или резолв с причиной («intentional»,
  «pre-existing», «stale-safe by design»). Открытый finding блокирует деплой.

## Риск-тиры (что блокирует)

Тир ставится по изменению, не по автору.

| Риск | Что | Гейт |
|---|---|---|
| High | `unified_sl.py`, `risk_manager.py`, `state_db.py` (схема/миграции), входы/выходы ордеров, ключи/креды | полный прогон + независимая сверка с биржей/RPC |
| Medium | `main_async.py`, `auto_entry.py`, `journal/*` (self-learn), `rpc.py`, `deploy.sh` | 1 раунд ревью + тесты |
| Low | `docs/*.md`, README, комментарии, `experiments/` | контрольные грепы, без ревью-раунда |

Сомневаешься → тир выше.

## Гейты (в порядке)

1. Автор сам: тесты + `py_compile` (для docs — контрольные грепы) ДО отправки на ревью.
2. Ревьюер — свежим контекстом, по diff, не по всему файлу.
3. Judge по `git diff`, не по файлу целиком.
4. Числа сверять с первоисточником: `state.db` / RPC / `systemctl`, не с пересказом.

## Директории/файлы (приоритет просмотра)

1. `main_async.py`, `unified_sl.py`, `auto_entry.py`, `risk_manager.py`, `rpc.py`, `state_db.py`
2. `journal/*.py` (самообучение — меняется чаще всего)
3. `docs/*.md` — только если трогается код, который они описывают
4. `bybit_ws/experiments/` — офлайн-стенд, не влияет на live; не блокировать live-фичи
